# Daybook — Daily Shopping Tracker

A responsive shopping and personal-record tracker built with React, TypeScript, Vite, Tailwind CSS and reusable shadcn-style UI primitives. Shared data is stored in separate Supabase Postgres tables for each data collection; `data/daybook.json` is the versioned initial seed. The optional Gmail test connector uses Google OAuth directly from the browser.

## Requirements

- Node.js 20.19+ or 22.12+
- npm

## Local setup

```bash
npm install
npm run dev
```

Open the local URL printed by Vite.

## Production build

```bash
npm run build
npm run preview
```

The static production site is written to `dist/`.

## Deploy to Vercel

Import the repository into Vercel and use the Vite defaults:

- **Framework preset:** Vite
- **Build command:** `npm run build`
- **Output directory:** `dist`

See [VERCEL-SUPABASE-CONFIGURATION.md](./VERCEL-SUPABASE-CONFIGURATION.md) for the environment-variable inventory, Supabase PostgreSQL pooler and CA setup, and security notes.

Or deploy with the Vercel CLI using `vercel` and `vercel --prod`. Application data is stored in Supabase, independently of source-code deployments.

## Data and privacy

For direct database development from VS Code, use a **separate Supabase development project**. The local database utility requires `SUPABASE_DEV_DB_URL` and `SUPABASE_DEV_PROJECT_REF` in the ignored `.env.local`; it rejects the current production project reference and requires the URI's project reference to match. It supports listing tables, bounded selects, parameterized insert/update/delete, bulk inserts, and creating basic tables. All write commands require interactive confirmation; update/delete require non-empty filters. Example commands: `npm run db:test`, `npm run db:tables`, `npm run db:select -- my_table 50`, `npm run db:create-table -- my_table '[{"name":"id","type":"uuid","primaryKey":true},{"name":"name","type":"text","nullable":false}]'`, `npm run db:insert -- my_table '{"id":"...","name":"Example"}'`, `npm run db:update -- my_table '{"name":"Updated"}' '{"id":"..."}'`, and `npm run db:delete -- my_table '{"id":"..."}'`. For file-based imports, `npm run db:insert-many -- my_table <json-file>` accepts a JSON array of up to 1000 records with matching fields; a future CSV workflow can map its headers to database columns and call the same bulk-insert method. These developer scripts do not run as part of Vite or Vercel and do not alter the production app. Do not configure production credentials in the development variables. The Vercel deployment continues using its existing `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (server-only), and `DATA_ACCESS_PASSWORD` variables.

Supabase schema migrations are not run by Vercel deployments. For app schema changes, review and explicitly run the relevant SQL migration only after checking its compatibility with the deployed app. The local data utility is not a migration runner. Keep `.env.local` private and never commit or expose database credentials in a `VITE_` variable. The app uses a signed, HTTP-only, same-site session cookie. Use the same Daybook password on each device. This is one shared password, not separate user accounts; anyone who knows it can access the shared records. Sessions last seven days. The browser never connects to Supabase directly; Vercel API handlers authenticate requests and access the server credentials.

After deploying the current app, if it asks how to initialize, choose **Use Git seed data** first. Then open **Data management → Restore a backup** and import the old `data/daybook.shared.json` file to populate the Supabase tables. Download that file privately from the old repository; it includes personal information and an encrypted credential vault, so do not commit or share it. The app validates the backup before saving. The API writes each collection as rows in its own Supabase table; record fields are preserved in each table's `record` JSONB column, and child records and relationships are stored in linked tables. Shopping lists, purchases, trips, products, stores, reminders, stocks, brokers, price snapshots, assets, daily learning records, dated training sessions, education records and their subjects/assessments/payments, personal education and career profile, family members, vehicles and their journeys/maintenance, electricity readings, subscriptions and transaction histories, devotional and prayer records, cooking recipes, cooking plans and their ingredients, daily cooking logs, issues and maintenance, personal documents, and the encrypted credential vault are all included. Favorites and display preferences are stored separately in the service-role-only `daybook_preferences` table, follow the same login across devices, and are included in JSON backups. Changes autosave; open devices check for updates on focus and every two minutes. Database revisions detect concurrent edits and report conflicts instead of silently replacing remote changes. JSON backup, Excel-compatible purchase CSV export, refresh, and confirmed clear-data controls are available under **Data management**.

The top bar lets you switch between light and dark mode and quickly toggle grouped or flat navigation. By default, sidebar screens are arranged in collapsible categories, with the current section opened automatically. Under **Data management → Navigation menu**, choose whether grouping is enabled and whether pages use their current order or alphabetical order. Data management also lets you choose which screen summaries appear on the Dashboard, including Mind & habits, AI Prompts, Subscriptions & bills, and Documents, alongside the other record modules. A visual theme (Sage studio, Cloud canvas, Warm sand, or Blush pink), display currency (INR by default, with USD, EUR and GBP available), font family (system UI, Inter, Arial, Roboto, Segoe UI, Georgia, Times New Roman, Trebuchet MS, Verdana, Tahoma, or Courier New), font style (modern, editorial, or rounded), six interface sizes from extra small (82%) to maximum (124%), accent color, and a dark background theme are also configurable. The Blush pink theme uses soft pink surfaces and works in light and dark mode; it retains the separately selected accent color. Font choices use local system fonts and sensible fallbacks. Dashboard cards show recent records and link to their corresponding screens. Changing currency updates formatting only; it does not convert existing amounts.

Use **Global search** from the sidebar or the top bar to find text across saved records and notes. Select a result to view its record details and jump to the screen that manages it. Results are links, so the browser context menu can open a selected record’s details in a new tab. Passwords and encrypted credential data are excluded from search.

Use **Documents** to store files in the private `daybook-documents` Supabase Storage bucket or add an external HTTPS document link; either option is supported, and both can be saved on one record. Uploaded files remain in Supabase Storage across app refreshes and deployments. Document metadata and links are stored in the `documents` Supabase table, and saves are confirmed before the form closes. Vercel's local filesystem is ephemeral and is not used for permanent document storage. Uploads are limited to 10 MB per file. Apply both `20261106130000_add_private_document_storage.sql` and `20261106180000_add_document_records_storage.sql` for document storage and persistence.

Pages adapt to phone and tablet widths with a compact navigation bar, single-column layouts where needed, and card-style shopping and history rows on narrower screens. On mobile widths, app date fields use separate month, day, and directly editable year controls; desktop date inputs and the operating system's date selection remain unchanged.

Use **Master data** to save reusable products with a category, unit and estimated price per unit, stores with optional plain-text locations, and custom reminder categories. Products and stores can be edited or copied. Reminder categories remain available even when no current reminder uses them; a category in use cannot be deleted until its reminders are reassigned or removed. Product presets can be selected when adding an item; quantities such as kg, g, L, ml, pcs, and other common units are supported, and the estimated total is calculated as quantity multiplied by the per-unit price. Saved stores are available when planning a shopping trip. Store locations are text only; map integration is not included.

Use **Notes & reminders** to add dated notes with a category, choose from grouped category buttons, search across reminder titles, categories, dates, details, and status, or filter by category and completion. Reminders display as full-width rows and can be edited directly in place. Add custom categories under **Master data → Reminder categories**. Due and overdue reminders, plus reminders due within the next seven days, appear on the dashboard. Use **Stocks** to save NSE/BSE stock codes and display names, group them with manually managed broker labels, enter average buy price per share and number of shares held, refresh quotes, and review dated price snapshots. Filter the compact stock rows by ticker/name/broker, exchange, broker, whether you hold shares, and quote availability. Sort by ticker, name, broker, latest price, quantity, holding value, or profit/loss in either direction; optionally group rows into collapsible broker or exchange tree nodes. The same code and exchange can be tracked separately for different brokers; duplicates for the same broker are prevented. On databases created with the earlier schema, run `supabase/migrations/20261106220000_allow_stock_codes_across_brokers.sql` in the Supabase SQL Editor to remove the old global ticker constraint. The **Import screenshot** action uses in-browser OCR to read tickers, quantities, and average prices from their table columns. Review and correct recognized values before saving; choose one broker for every row or override it individually. Screenshot text is processed in the browser. New seed data starts with no sample holdings. Migrating older browser data preserves its saved watchlist and price snapshots. When the average buy price, quantity, and an INR quote are available, the app calculates invested value, current value, and unrealized profit/loss. Holdings inputs are optional; leave both empty if you only want a watchlist. Quotes are requested from Yahoo Finance first; when that provider cannot return a quote, the server can fall back to Twelve Data if `TWELVE_DATA_API_KEY` is configured. Obtain an API key from Twelve Data and add it as a server-side environment variable in Vercel; for local development, add it to `.env.local` (never commit the real key). Provider coverage, freshness, free-tier limits, and exchange support vary, so this cannot guarantee quotes for every security. If both providers miss a stock, use **Enter price** on that stock’s row to save a verified INR price and timestamp; later provider refreshes add newer snapshots. Quote providers are not broker feeds; prices may be delayed or unavailable. Verify prices with your broker before making financial decisions. Stock lists, holdings inputs, and snapshots are stored in Supabase; no broker account or trade data is connected.

Use **Account credentials** for account/provider names, HTTPS sign-in links, usernames, passwords, recovery information, tags, notes and searchable custom fields. Before saving, the browser encrypts the vault with AES-256-GCM using a separate passphrase-derived key (PBKDF2-SHA-256); only encrypted data is stored in Supabase. Use a unique vault passphrase on each device. It is not the Daybook access password and is never sent as part of the save request. If forgotten, the vault cannot be recovered. Lock the vault when finished. This protects stored data, not a compromised browser, device or deployed app; while unlocked, the app handles decrypted values in browser memory. This is not a substitute for a dedicated password manager; do not store bank PINs, one-time codes or recovery codes. The fictional example in the add form is not saved unless you submit it.

## Supabase and Gmail setup

1. In your Supabase project, open **SQL Editor**, run `supabase/migrations/20261105010000_normalize_daybook_storage.sql`, and confirm the collection tables and `public.load_daybook_data` / `public.save_daybook_data` functions are created. If you already ran the earlier single-table migration, this migration keeps and converts its shared row.
2. Set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in Vercel Environment Variables. Use the project URL and a server-only service role key. Never use a `VITE_` prefix for the service role key or commit it. Also set `DATA_ACCESS_PASSWORD` to a strong passphrase of at least 16 characters, then redeploy.
3. Optional: the **Database manager** and **Hosting & storage** screens need `SUPABASE_DB_URL`, a PostgreSQL URI from your Supabase project's **Connect** dialog for the same project as `SUPABASE_URL`. Choose **Transaction pooler** for Vercel and keep it server-only. If TLS certificate verification fails, download the project's CA certificate from **Database → Settings → SSL Configuration**, base64-encode the certificate file, and set the result as the server-only `SUPABASE_DB_CA_CERT_BASE64` variable. The app trusts that CA while keeping certificate verification enabled. Redeploy after setting either variable. The manager lists public tables, functions, procedures, and triggers, reads up to 50 rows per page, and includes a guarded SQL console. It accepts one `SELECT` (with a literal `LIMIT` from 1 to 100), `INSERT` (up to 100 `VALUES` rows), `UPDATE`, or `DELETE` statement at a time; table references must be qualified with `public.`. SELECT runs in a read-only transaction. Writes require a `WHERE` clause for `UPDATE` and `DELETE`, a review step, an acknowledgement checkbox, and typing the exact command-specific confirmation phrase. DDL, transactions, subqueries, function calls, protected core tables, `RETURNING`, `ON CONFLICT`, and multiple statements are blocked. SQL writes are permanent, bypass the Daybook archive, and can activate database triggers or foreign-key cascades; download a JSON backup first. Access is protected by the shared Daybook password, so protect that password and database credentials.
4. For local API development, copy `.env.example` to `.env.local` and set `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `DATA_ACCESS_PASSWORD`, and, if using the Database manager or Hosting & storage screen, `SUPABASE_DB_URL`; set `SUPABASE_DB_CA_CERT_BASE64` when your database requires a custom CA certificate. Then run `npm run dev`. `.env.local` is ignored by Git.
5. Open the app and sign in. If the database is not initialized, choose **Use Git seed data**; then use **Data management → Restore a backup** to import `data/daybook.shared.json` downloaded privately from the old repository. The import is what loads those records into their corresponding tables. A local-only SQL script containing the old backup is generated at `supabase/manual-import-daybook.sql`; it is excluded from Git because it contains personal information. The old shared data file and browser secrets are intentionally not copied into this repository.
6. Gmail is separate and optional. In Google Cloud Console, enable the **Gmail API**, configure OAuth consent, and create a Web application OAuth client. Add your local and deployed origins, set `VITE_GOOGLE_CLIENT_ID` in `.env.local` and Vercel Environment Variables, and redeploy.
7. To test email, select **R&D / Test Connectors**, click **Connect Gmail**, and follow the authorization prompt. The email is sent from the Google account you authorize.

For a local-only UI/data preview while diagnosing sign-in, set `LOCAL_AUTH_BYPASS=true` in `.env.local` and run `npm run dev`. This skips the password only for requests addressed to `localhost`, `127.0.0.1`, or `::1`, and only outside production. It still requires the local Supabase server credentials to load cloud data. Never enable this in Vercel or expose the development server to your network. Remove the setting or set it to `false` after testing.

Gmail API sending is a test-email connector, not a scheduled reminder system.

## AI Prompts storage

Before deploying the AI Prompts screen to an existing database, back up your data and run `supabase/migrations/20261106140000_add_ai_prompt_storage.sql` in the Supabase SQL Editor. It creates the service-role-only `public.prompt_records` table and updates the existing Daybook save/load functions to persist and restore prompts, including title, description, prompt text, tool, type, and category. The app preserves prompt order and archive/restore behavior. To inspect saved prompts, run `select id, position, record ->> 'title' as title, record ->> 'tool' as tool, record ->> 'type' as prompt_type, record ->> 'category' as category from public.prompt_records order by position;`.

## Mind & habits

Use **Mind & habits** for daily habit tracking and personal reflection, not as a medical assessment. In the **Habit tracker** tab, set a start date and an optional target duration, check habits for a selected date, and see completed-day progress. Ongoing habits without a target show elapsed days; extend a target by seven days or edit its duration. In **Reflections**, record an emotion, its intensity, what was happening, how you responded, a positive action, and what you might try next time. Search or filter past reflections by emotion. Habits and reflections can be edited or moved to **Archive**, and archived records can be restored. The screen does not provide diagnoses or treatment advice.

Before deploying this screen to an existing database, back up your data and run `supabase/migrations/20261106150000_add_mind_habits_storage.sql` in the Supabase SQL Editor. It creates service-role-only tables for habits and reflections and updates the Daybook save/load functions. Habit start dates, target durations, and check-in dates use the existing JSON records, so they require no additional database migration. These collections are also included in JSON backups.

Before deploying the devotional resource library to an existing database, back up your data and run `supabase/migrations/20261106160000_add_devotional_resources.sql` in the Supabase SQL Editor. It creates a service-role-only table for links and adds the collection to the Daybook save/load functions. Resource records are included in JSON backups and the Archive.

Before deploying **Subscriptions & bills** to an existing database, back up your data and run `supabase/migrations/20261106170000_add_subscriptions_storage.sql` in the Supabase SQL Editor. It creates a service-role-only table for service accounts and their transaction histories and adds the collection to the Daybook save/load functions. Records are included in JSON backups and the Archive.
